    CellItemLayer, CellObjectLayer, CellEntityLayer — concept, lifecycle, frame cycle, rendering & entities

    This document explains the “cell item” layer family:

    • CellItemLayer (base data + transforms per cell)
    • CellObjectLayer (renders per-cell objects via IBulkRenderer / BulkRendererAsset)
    • CellEntityLayer (spawns/despawns ECS entities per cell and keeps them in sync)

    It focuses on:

    • how the layers store data
    • how dirty tracking affects recalculation
    • what happens every frame (update → calculate → render → cleanup)
    • initialization and disposal responsibilities
    • how to use each layer correctly

    1) Core idea: “an item per cell”

    A cell item layer represents at most one logical thing per cell (a tile prop, a building, a resource entity, etc.). The thing is described by:

    • Item index: what is in the cell (ItemIndexMap)
    • Item state: a variation or stage (ItemStateMap)
    • Local transform parts:
      • ItemPositionMap (float3)
      • ItemRotationMap (quaternion)
      • ItemScaleMap (float3)
    • Precomputed local matrix:
      • ItemTransformMap (Matrix4x4) = combined local TRS (plus optional transform settings)

    These fields live in CellItemLayer (Runtime/CellItems/Data/CellItemLayer.cs).

    2) CellItemLayer: data, dirty tracking, update, serialization, disposal

    2.1 Data layers inside CellItemLayer

    CellItemLayer allocates a “per cell” data layer for each attribute:

    Field Type Meaning
    ItemIndexMap ColorMapCellValueDataLayer_Int cellIndex -> itemIndex (also has a color map for visualization)
    ItemStateMap CellValueDataLayer<int> cellIndex -> state
    ItemPositionMap CellValueDataLayer<float3> cellIndex -> local position
    ItemRotationMap CellValueDataLayer<quaternion> cellIndex -> local rotation
    ItemScaleMap CellValueDataLayer<float3> cellIndex -> local scale
    ItemTransformMap CellValueDataLayer<Matrix4x4> cellIndex -> local transform matrix

    Each is chunked and has:

    • IsDirty flag
    • per-chunk dirty grid (ChunkDirtyGrid)
    • job dependency tracking (PrepareToRead, PrepareToWrite, AddReadDependency, AddWriteDependency)

    This is why updates can run “only when something changed”.

    2.2 Initialization

    CellItemLayer.Init(HexTerrainSettings settings) ensures all maps exist and are sized to settings.CellsCount.

    CellItemLayer.Init<TInitArgs>(..., initArgs) applies configuration when initArgs implements ICellItemLayerConfig:

    • ItemTransformSettings
    • SurfaceLayerReference
    • OverlapSurfaceLayerReference
    • initial data fill for index/state/pos/rot/scale (via InitDataLayer(...) helpers and InitColoredDataLayer(...) for index)

    2.3 Per-frame update: UpdateCellItems() → UpdateLocalTransforms()

    CellItemLayer.UpdateCellItems(dependency) primarily calls:

    • UpdateLocalTransforms(dependency)

    UpdateLocalTransforms:

    • returns early if ItemPositionMap, ItemRotationMap, and ItemScaleMap are not dirty
    • schedules CalculateCellItemTransformsJob
    • writes ItemTransformMap and marks it dirty

    So the base layer’s “output” that other layers consume is typically:

    • ItemIndexMap
    • ItemStateMap
    • ItemTransformMap

    2.4 Serialization

    CellItemLayer implements ISerializableTerrainLayer:

    • SerializeLayer(BinaryWriter) serializes: index/state/pos/rot/scale
    • DeserializeLayer(BinaryReader, settings) restores the same and then calls SetAllDirty(true)

    Notes:

    • It calls CompleteAllJobs() before serializing/deserializing to ensure data safety.

    2.5 Cleanup vs Dispose

    There are 3 different “end of frame / end of life” concepts:

    • Cleanup() / CleanupAsync(...)
      Clears dirty flags/chunk dirty grids (so next frame won’t recompute unless something changes again).

    • Dispose()
      Permanently frees native memory (NativeList, NativeParallel... collections) owned by the layer.

    • CompleteAllJobs()
      Synchronization point used before serialization or when safe CPU reads are required.

    3) Frame cycle overview (how derived layers fit in)

    flowchart TD 
A["Gameplay writes: ItemIndex/State/Pos/Rot/Scale"] --> B["Dirty flags are set on changed chunks"] 
B --> C["Update phase: CellItemLayer.UpdateCellItems()"] 
C --> D["Job: compute ItemTransformMap (local matrices)"] 
D --> E["Derived layer calculates view data"] 
E --> F["Render or ECS updates happen"] 
F --> G["Cleanup phase: clear dirty flags (Cleanup()/CleanupAsync(JobHandle))"]

    Derived layers differ mainly at step E/F:

    • CellObjectLayer: builds render batches (BulkRenderItemsDataLayer) and calls IBulkRenderer to draw.
    • CellEntityLayer: decides which ECS entities should exist per cell, instantiates/destroys them, and systems update their transform/visibility.

    4.1 What CellObjectLayer adds on top of CellItemLayer

    CellObjectLayer inherits all base “item” data and adds:

    • IBulkRenderer BulkRenderer
    • LOD selection config:
      • NativeList<CellObjectLayerLODSettings> LODSettings
      • int LODsCount
    • Baked visuals data (copied into native memory on init):
      • NativeList<CellObjectVisualItemSettings> AllCellObjectVisuals
      • NativeList<CellObjectLODSettings> AllCellObjectsLODSettings
    • Render outputs per LOD:
      • List<BulkRenderItemsDataLayer> VisualsByLODLayer
        • each is a NativeParallelMultiHashMapDataLayer<BulkRenderItemSettings, BulkRenderItem>

    Capacity detail:

    • each LOD output is initialized to Settings.CellsCount * MaxSubmeshesPerCell
    • because NativeParallelMultiHashMap capacity must be known up-front for job writes

    4.2 Baking step (Editor): precomputing BulkRenderItemSettings

    The key performance concept: render setup is baked once (mesh/material/submesh/property block selection) and runtime only computes transforms.

    CellObjectLayerConfigAsset.BakeCellObjectConfigs() does this:

    1. Iterates ObjectConfigs (list of CellObjectConfigAuthoring)
    2. Each authoring contains multiple states (CellObjectPrefabAuthoring)
    3. Each state contains multiple LODs (CellObjectPrefabLODAuthoring)
    4. Each LOD has a list of MeshRenderers to be rendered

    For each MeshRenderer:

    • it calls bulkRenderer.RegisterRenderer(renderer, meshFilter, ...)
    • which returns a list of BulkRenderItemSettings describing what to draw
      • mesh index, material index, submesh index, layer, shadows, property block index, etc.

    Then the baker stores:

    • CellObjectVisualItemSettings:
      • RenderItemSettings (the baked “what to draw”)
      • Transform (renderer’s localToWorldMatrix as a relative transform)
    • CellObjectLODSettings ranges per (objectIndex, state, lodIndex):
      • VisualsStartIndex
      • VisualsCount
      • HasVisuals

    At runtime, CellObjectLayer.Init(...) copies these baked lists into:

    • AllCellObjectVisuals (native)
    • AllCellObjectsLODSettings (native)

    4.3 Runtime calculation: converting cell data into render batches

    Core entrypoints:

    • CalculateCellObjects(...)
    • CalculateCellObjectsLODSs(...)
    • CalculateCellObjectsLOD(...)

    CalculateCellObjectsLOD(...) does:

    • early-out unless something relevant is dirty:
      • ItemIndexMap, ItemStateMap, ItemTransformMap
      • surface metrics dirty (surfaceLayer.CellMetricsMap, optional overlap surface)
      • visibility dirty (new visible chunks in chunksLayer.ChunkVisibility)
    • clears the LOD render batch:
      • renderItemsDataLayer.Data.ClearNativeParallelMultiHashMapAsync(...)
    • schedules one of:
      • CalcCellObjectsLODLayerJob
      • CalcCellObjectsLODLayerJob_OverlapSurface

    Job behavior (per cell):

    • skip if the cell’s chunk is not visible (ChunkVisibilityGrid[chunkIndex].IsVisible == false)
    • read:
      • cellObjectIndex = ItemIndexMap[cellIndex]
      • cellObjectState = ItemStateMap[cellIndex]
    • compute the state/LOD lookup index:
      • cellObjectIndex * StatesCountPerObject * LODsCount + cellObjectState * LODsCount + LODIndex
    • for every visual in that LOD:
      • produce a BulkRenderItem with a final matrix:
        • chunkTransform * (cellMetrics.CellTransform_Local * ItemTransformMap[cellIndex]) * visual.Transform
      • add it to NativeParallelMultiHashMap under key visual.RenderItemSettings

    Result:

    • VisualsByLODLayer[lodIndex] becomes a grouped set of “instances to draw” keyed by BulkRenderItemSettings.

    4.4 Rendering: CellObjectLayer.RenderLODs(...) → IBulkRenderer

    Render path:

    • CellObjectLayerGroup.Render(camera, normalizedCameraZoom) calls CellObjectLayer.Render(...)
    • RenderLODs selects one LOD based on normalizedCameraZoom and LODSettings
    • then calls Render(camera, BulkRenderer, renderEntitiesLOD)

    Render(...):

    • opens the render batch data layer for read
    • computes a conservative worldBounds
    • calls:
      • IBulkRenderer.RenderEntities(renderItemsDataLayer.Data, camera, worldBounds)

    5) IBulkRenderer / BulkRendererAsset: how batched data becomes draw calls

    Files:

    • Runtime/BulkRendering/IBulkRenderer.cs

    5.1 What IBulkRenderer provides

    IBulkRenderer is both:

    • a registry for meshes/materials/property blocks
    • and a renderer that consumes batched BulkRenderItems

    Key responsibilities:

    • registration:
      • RegisterMesh, RegisterMaterial, RegisterPropertyBlock, RegisterRenderer(...)
    • rendering:
      • RenderEntities(...) overloads for different input forms

    5.2 Default implementation: BulkRendererAsset

    BulkRendererAsset stores:

    • List<Mesh> Meshes
    • List<Material> Materials
    • List<MaterialPropertyBlock> PropertyBlocks
    • dictionaries to keep unique indices per asset instance id

    When RegisterRenderer(renderer, meshFilter, result, ...) is called:

    • it inspects the mesh and renderer materials
    • it registers mesh/material/property blocks into the asset lists if needed
    • it appends one or more BulkRenderItemSettings describing:
      • which mesh
      • which submesh
      • which material
      • shadow and layer flags
      • optional property block index

    This is the “precalculation” step that allows runtime to remain lightweight.

    5.3 How draw calls are issued

    BulkRendererUtils.Render(...) chooses:

    • Graphics.DrawMesh for a single instance
    • Graphics.DrawMeshInstanced / Graphics.RenderMeshInstanced for many instances

    The renderer groups by BulkRenderItemSettings so each group becomes one instanced draw call (or a few calls, if the group is large).

    6.1 What CellEntityLayer adds

    On top of CellItemLayer, it adds:

    • CellEntityViewDataLayer CellEntityViews
      • stores CellEntityView { Prefab, Instance } per cell
      • also stores request buffers:
        • CreateEntityRequests: prefab -> cellIndex
        • RemoveEntityRequests: instance -> cellIndex
        • ClearedCells
        • EntityByChunkIndex
    • NativeList<CellEntityConfig> CellEntityConfigs
      • per entity index configuration (color + prefab mapping per state)
    • EntityManager EntityManager
    • an EntityCommandBuffer used to add components/shared components from jobs:
      • SetChunkIndexCommandBuffer
      • SetChunkIndexCommandBufferDependency

    6.2 Step 1 — Decide what entities should exist: CalculateEntities()

    CellEntityLayer.CalculateEntities(dependency):

    • early-out if nothing dirty:
      • ItemIndexMap, ItemStateMap, CellEntityViews
    • clears and re-inits request structures:
      • CellEntityViews.ClearRemoveAndCreateRequests()
      • CellEntityViews.Init(Settings.CellsCount, Settings)
    • merges dirty grids from ItemIndexMap and ItemStateMap into CellEntityViews
    • schedules CalcCellEntityEntitiesJob

    CalcCellEntityEntitiesJob (per dirty cell):

    • reads (cellEntityIndex, cellEntityState)
    • uses CellEntityConfigs[cellEntityIndex] to compute neededPrefab:
      • it matches cellEntityState against StatePerPrefab
    • compares to current view (CellEntityViews[cellIndex].Prefab)
    • emits:
      • remove request if a prefab was previously present
      • create request if a prefab is now required
      • cleared cell index if it was removed and not replaced

    No structural changes happen here; it only computes requests.

    6.3 Step 2 — Apply requests: UpdateEntities(...)

    CellEntityLayer.UpdateEntities(layerEntity, layerIndex, dependency):

    • early-out unless CellEntityViews.IsDirty

    Then it:

    1. Creates an ECB (SetChunkIndexCommandBuffer = new EntityCommandBuffer(Allocator.TempJob)).
    2. Iterates unique prefabs in CreateEntityRequests:
      • EntityManager.Instantiate(prefab, requestsCount, Allocator.TempJob)
    3. Schedules SaveCreatedCellEntityEntitiesJob per prefab:
      • fills CellEntityViews[cellIndex] = { Prefab, Instance }
      • adds instance into EntityByChunkIndex
      • enqueues structural additions via ECB:
        • CellEntityTerrainReference { Value = terrainEntity } (shared)
        • HexChunkGridIndex { Value=chunkIndex, TerrainEntity, LayerIndex } (shared)
        • HexCellIndex { Value = cellIndex } (component)
    4. Schedules SaveClearedCellEntityEntitiesJob:
      • sets CellEntityViews[cellIndex] = { Entity.Null, Entity.Null } for cleared cells
    5. Destroys instances in RemoveEntityRequests on the main thread:
      • EntityManager.DestroyEntity(entitiesToRemove)

    Why ECB here:

    • the code instantiates on the main thread, but adding shared components for many entities is pushed into a job via EntityCommandBuffer.ParallelWriter, then played back later.

    6.4 Step 3 — Playback structural changes: PlaybackUpdateCellEntityCommandBuffersSystem

    PlaybackUpdateCellEntityCommandBuffersSystem runs in HexTerrainsStartPreRenderGroup and calls:

    • layer.PlaybackSetChunkIndexCommandBuffer()

    PlaybackSetChunkIndexCommandBuffer():

    • completes SetChunkIndexCommandBufferDependency
    • plays back the ECB into EntityManager
    • disposes the ECB

    This is the point when the spawned entities actually receive their terrain/chunk/cell components.

    7) Keeping entity transforms and visibility updated (data changes → ECS state)

    System:

    • UpdateCellEntityLayerEntitiesStateSystem (Runtime/CellEntities/Systems/UpdateCellEntityEntitiesStateSystem.cs)

    Update group ordering:

    • runs in HexTerrainsStartPreRenderGroup
    • runs after PlaybackUpdateCellEntityCommandBuffersSystem
      • so newly spawned entities have the required components before transform updates

    7.1 What it updates

    Depending on what changed, it updates:

    • PostTransformMatrix (entity transform)
    • CellEntitityVisibility (a component storing a bool Value)

    7.2 When it runs per layer

    For each terrain and each CellEntityLayer, it checks dirtiness:

    • “data dirty” if any of these are dirty:
      • surface CellMetricsMap (and optional overlap surface metrics)
      • chunk visibility map has newly visible chunks
      • cellEntityViews.IsDirty
      • cellItemTransforms.IsDirty (ItemTransformMap from CellItemLayer)
    • “visibility dirty” if HexTerrainVisibility component changed on the terrain entity since last update

    Then it chooses one path:

    • only data dirty → UpdateCellEntitiesState(...)
    • only visibility dirty → UpdateCellEntitiesVisibilities(...)
    • both → UpdateCellEntitiesStateAndVisibilities(...)

    7.3 How the transform is computed

    UpdateCellEnitiesStateJob / UpdateCellEntitiesStateAndVisibilityJob computes per entity:

    • find chunkIndex from the entity’s shared HexChunkGridIndex
    • skip whole chunk if no relevant dirty grids are set for that chunk
    • read cellIndex from HexCellIndex
    • compute cellPosition:
      • CellMetrics[cellIndex].CenterPosition_Global
      • plus ChunkVisibilityMap[chunkIndex].ChunkOffset (if present)
    • final matrix:
      • (Matrix4x4)terrainLocalToWorld * TRS(cellPosition + TransformSettings.Position, TransformSettings.Rotation, TransformSettings.Scale) * LocalTransforms[cellIndex]
    • writes to PostTransformMatrix

    If overlap surface is used, the job variant chooses the higher surface metrics before computing.

    7.4 How visibility is applied

    • If only terrain visibility changed:
      • UpdateCellEntitiesVisibilityMarkerJob writes CellEntitityVisibility.Value = isTerrainVisible for all matching entities.
    • If both changed:
      • UpdateCellEntitiesStateAndVisibilityJob updates both visibility and transforms in one pass.

    8) Practical usage guide

    8.1 Using CellObjectLayer (rendered, non-ECS)

    1. Create a CellObjectLayerConfigAsset.
    2. Assign a BulkRendererAsset to BulkRenderer.
    3. Fill ObjectConfigs with CellObjectConfigAuthoring entries:
      • each entry references state prefabs (CellObjectPrefabAuthoring)
      • each state contains LOD authorings (CellObjectPrefabLODAuthoring) with MeshRenderer lists
    4. Ensure baking runs (the asset runs BakeCellObjectConfigs() on OnValidate).
    5. At runtime:
      • set ItemIndexMap / ItemStateMap to choose the object + state
      • optionally set local position/rotation/scale maps
      • call UpdateCellItems() to update ItemTransformMap
      • call CalculateCellObjectsLODSs(...) to populate render batches
      • call CellObjectLayerGroup.Render(camera, normalizedCameraZoom) to draw

    8.2 Using CellEntityLayer (ECS entities per cell)

    1. Create a CellEntityLayerConfigAsset and set CellEntities authoring list.
    2. Ensure baking produces a NativeArray<CellEntityConfig> on the terrain (consumed by CellEntityLayerGroup.Init(...)).
    3. At runtime:
      • set ItemIndexMap[cellIndex] to the entity type index
      • set ItemStateMap[cellIndex] to choose which prefab to spawn for that entity type
    4. Per update cycle:
      • CellEntityLayerGroup.CalculateEntities(...) schedules request calculation
      • CellEntityLayerGroup.UpdateEntities(terrainEntity, ...) instantiates/destroys and queues ECB additions
      • PlaybackUpdateCellEntityCommandBuffersSystem plays back ECB (adds terrain/chunk/cell components)
      • UpdateCellEntityLayerEntitiesStateSystem updates transforms/visibility based on dirty data

    9) Disposal responsibilities and common pitfalls

    9.1 Don’t confuse Cleanup() with Dispose()

    • Cleanup() is expected to run every frame (or periodically) to clear dirty flags.
    • Dispose() must run when the terrain/layer is destroyed to release native memory and, for CellEntityLayer, ensure spawned entities are destroyed.

    9.2 Entity destruction on layer disposal/resize

    CellEntityViewDataLayer overrides item disposal:

    • when a CellEntityView item is disposed, it destroys item.Instance via EntityManager.DestroyEntity(...) (if it exists)

    It also tracks “discarded cells” on Init(layerSize) and adds their entities to removal requests, preventing leaks when terrain shrinks.

    9.3 Ensure correct ordering for entities

    For correct results, entity lifecycle typically requires this order:

    1. calculate spawn/despawn requests
    2. instantiate/destroy entities
    3. playback ECB that adds required components
    4. update transform + visibility

    The built-in system ordering enforces this via HexTerrainsStartPreRenderGroup and [UpdateAfter(typeof(PlaybackUpdateCellEntityCommandBuffersSystem))].
