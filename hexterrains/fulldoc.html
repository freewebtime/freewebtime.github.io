    HexTerrains Framework

    The HexTerrains Framework is a high-performance, ECS-based system for building and managing hexagonal terrains in Unity. Built for large-scale simulations, it's ideal for games like strategy titles, city-builders, and economic simulations. This README provides a high-level overview to help you get started.

    Features

    • ⚡ Extremely fast terrain updates and rendering via Unity DOTS (ECS + Jobs + Burst)
    • 🧱 Modular terrain layers: height, biomes, cell items, and entities
    • 🖌️ In-game Photoshop-style terrain editor with brush tools
    • 🧭 Serialized save/load system with extensible architecture
    • 🧩 Plug-and-play design for custom gameplay or UI logic

    • Full-featured user tool editor

    0. Introduction

    The HexTerrains Framework is a high-performance, ECS-based system for building and managing hexagonal terrains in Unity. It’s built on top of Unity DOTS and designed for simulation-heavy games like strategy, city-building, or economic sims. With a modular layer system and efficient jobified pipelines, it supports in-game editing, serialization, and advanced rendering workflows.

    1. Architecture Overview

    • Core System: Unity DOTS (ECS, Jobs, Burst)
    • Data Abstraction: TerrainLayers and DataLayers
    • Update Groups: Simulation broken into modular execution groups (init, prerender, render, cleanup)
    • Tooling: Photoshop-like user tools with UI Toolkit binding
    • Rendering: Custom chunk-based mesh generation with color maps and ECS-friendly systems

    2. HexTerrain Core Concepts

    • Chunks: Terrain is divided into rectangular chunk grids for efficient updates and rendering.
    • Layers: Each aspect of the terrain (height, biome, items, entities) is stored in a TerrainLayer.
    • DataLayers: Provide per-layer data management, including dirty grid tracking and custom memory layout.

    3. Terrain Layers Explained

    The terrain in HexTerrains Framework is built as a stack of modular layers. Each layer is responsible for storing, updating, and optionally rendering a specific aspect of the terrain. For clarity, each terrain layer has its own documentation:

    • SurfaceLayer — manages cell height and biome data, color mapping, and base mesh generation.
    • AreasLayer — stores flags like provinces, ownership zones, or other categorical data using one byte per cell.
    • CellItemsLayer — handles static props or decorations per cell, rendered via instancing.
    • CellEntitiesLayer — stores dynamic ECS entities (e.g., buildings, characters) with full lifecycle and rendering logic.

    Each layer implements a version of HexTerrainLayerBase, and may include:

    • A custom data layer (e.g., DataLayer<T>)
    • A rendering component (if visible)
    • Authoring and creation logic (via baking or runtime commands)

    Refer to the individual .md files above to understand how each layer works, including data flow, editing support, and rendering pipeline integration.

    • SurfaceLayer: Stores height and biome per cell. Also manages render mesh and color mapping.
    • AreasLayer: Byte-per-cell storage for flags like provinces, build zones, or player ownership.
    • CellItemsLayer: Static objects placed per cell, rendered using custom instancing (RenderEntity).
    • CellEntitiesLayer: Dynamic ECS entities (e.g., buildings, units) per cell, with sync and state tracking.

    5. Editor & User Tools

    The HexTerrains Framework includes a flexible and modular in-game editing system inspired by Photoshop tools. The editor is centered around a state machine architecture, with tools implemented as independent states derived from BrushUserToolState.

    Editor tools are rendered using Unity UI Toolkit and are fully bound to live data via UIDataSource classes. This makes it easy to create in-game editors with two-way binding and update propagation.

    Tool Architecture

    • UserToolsStateMachine — central controller for tool switching and lifecycle.
    • IUserToolAPI — interface used by tools to interact with terrain data in a safe, non-ECS way.
    • UserToolAPI — default implementation of IUserToolAPI, provides convenience methods for common terrain operations.
    • BrushUserToolState — abstract base class for brush-style tools.

    Example Tools

    Each tool inherits from BrushUserToolState or its subtypes:

    • PaintCountriesUserToolState — paints country data (ownership, etc.) onto cells.
    • DeformGroundUserToolState — applies height deformation to the ground layer.
    • ApplyHeightmapUserToolState — uses external textures or data to modify terrain elevation.
    • AutoPaintUserToolState — paints based on cell conditions (biome, elevation, etc.)
    • AddNoiseUserToolState — procedurally adds noise to terrain elevation.
    • LevelTerrainUserToolState — levels terrain to a target height.
    • PaintAreasUserToolState — sets province/area flags.
    • StampUserToolStateBase — base for object stamping tools (items, entities, etc.)
    • ToggleTerrainVisibilityUserToolState — hides or shows terrain layers (debugging).

    UI Binding

    All tools expose a tool-specific view model derived from UIDataSource. UI updates are handled through automatic version tracking — when a value is changed on the data source, the UI Toolkit binding system refreshes the relevant UI elements.

    Custom editors like UniversalToolSettingsScreen and ToolSettingsScreen are provided to present and edit tool options.

    See UserTools.md for full breakdown and guidance on extending the tool system.

    • BrushUserToolState: Core base class for most editing tools

    • State Machine: UserToolsStateMachine manages tool lifecycle

    • IUserToolAPI: Provides safe access to terrain data outside ECS context

    • Examples:

      • PaintCountriesUserToolState
      • DeformGroundUserToolState
      • ApplyHeightmapUserToolState
      • AutoPaintUserToolState

    6. Rendering Pipeline

    Rendering in the HexTerrains Framework is built around high-performance ECS-compatible mesh generation, GPU instancing, and a modular data pipeline. The rendering pipeline is responsible for visualizing terrain surfaces, items, and cell entities.

    For developers focused only on visuals, refer to the separate Rendering.md file.

    Surface Rendering

    • CalcGroundMeshSourcesSystem and CalcSurfaceMeshSourcesSystem compute geometry sources from surface data.
    • GenerateHexChunkMeshJob and GenerateHexChunkMeshWaterJob create the actual mesh geometry per chunk.
    • Color data (e.g., biome tints) is calculated using jobs like CalcCellBiomeColorsSystem.
    • Final rendering is handled by RenderHexSurfaceSystem, which instantiates or updates MeshInstances.

    Cell Items Rendering

    • Static decorations (like trees or rocks) are rendered using a custom instancing system.
    • Configured via RenderEntitiesConfig and rendered using RenderEntity abstraction.
    • Sorted for optimal GPU batching in SortRenderEntitiesJob.

    Cell Entities Rendering

    • Dynamic ECS entities (e.g. characters, animated props) are spawned per-cell from entity prefabs.
    • Meshes and states are updated in sync with game logic.
    • View data stored in HexCellEntityViewDataLayer.

    Visibility and Culling

    • CalcChunkVisibilitySystem computes visible terrain bounds per frame.
    • Only visible chunks are sent to rendering systems.
    • This chunk-based culling ensures maximum performance and minimal overdraw.

    Summary

    • All rendering logic runs in ECS-compatible systems

    • Most geometry and color generation happens in burst-compiled jobs

    • Visibility is managed by chunk-based frustum culling

    • Surface, Item, and Entity rendering are modular and extensible

    • Mesh generation happens in jobs (GenerateHexChunkMeshJob, GenerateHexChunkMeshWaterJob)

    • Mesh sources are calculated and marked dirty if needed

    • ECS camera frustum is used to cull chunks

    • Colors (e.g. biome visualization) are updated in background jobs

    10. UI Architecture

    The UI system in the HexTerrains Framework is built using Unity UI Toolkit and centers around data-driven binding via the UIDataSource architecture. The design encourages modular UI screens that can adapt to gameplay tools, editor contexts, or custom extensions.

    UIDataSource Pattern

    At the core of the UI logic is the UIDataSource base class. It acts as the view model for each UI screen and provides:

    • Property versioning (Version) to automatically trigger UI updates
    • Simple C# properties for UI binding
    • Change notification integration with Unity's UI Toolkit binding system

    Each UIDataSource implementation exposes tool-specific or screen-specific data and logic.

    UI Screens

    UI screens like UserToolsScreen, ToolSettingsScreen, and MinimapScreen follow a unified pattern:

    • Bind to a specific UIDataSource type
    • Use BindData or SetDataSource to associate with live view model
    • Automatically update on version changes
    • Use [UxmlAttribute] and [CreateProperty] for automatic UI Toolkit integration

    Minimap Integration

    The MinimapScreenBase and its MinimapScreenDataSource subclass demonstrate a UI component that is bound to terrain-level data, such as current view position and zoom level. It listens to and dispatches updates through binding, while keeping rendering and simulation logic separate.

    Template-based Lists and Views

    The UI system supports flexible UI lists through:

    • UIListView and SimpleListView wrappers
    • TemplateSelectorConfig and TemplateSelectorConfigByType to support dynamic templating
    • DataTemplateConfig for per-item UI generation

    These features enable complex tool lists, layer selectors, and item inspectors.

    Custom UI Elements

    You can create custom visual elements that bind to data via UXML and code attributes:

    • Inherit from VisualElement
    • Use [UxmlAttribute] and [CreateProperty]
    • Override SetValueWithoutNotify to handle data changes

    Example: MinimapCameraIndicator binds to a Vector2 normalized position and can react to updates from the terrain camera.

    Commit Changes Workflow

    Some UI screens implement ICommitChanges to allow buffering and committing changes made in the UI before applying them to runtime data. This allows undo-like behavior or edit previews.

    12. Surface Mechanics

    • Surfaces include ground and water
    • Biome and height stored per cell
    • Calculated via systems like CalcGroundCellMetricsSystem, CalcCellBiomeColorsSystem
    • Rendering flows into RenderHexSurfaceSystem

    13. Cell Items

    • Static prefabs rendered via instanced drawing
    • RenderEntity is the abstraction for instancing
    • Coloring and visibility handled in background jobs
    • Authoring via CellItemPrefabAuthoring, CellItemsLayerAuthoring

    14. Cell Entities

    • Each cell can hold an ECS entity with state
    • Entities updated via UpdateCellEntitiesSystem
    • View and state stored in HexCellEntityDataLayer, HexCellEntityViewDataLayer
    • Fully dynamic and supports animations, logic
    • Uses command buffers to spawn/despawn during simulation

    15. Performance Notes

    • Dirty chunk grid ensures only modified areas are updated
    • Most systems are fully burst-compiled jobs
    • Terrain data structures support fast parallel iteration
    • Editor tools are detached from simulation, can run in playmode

    16. Extending the Framework

    • Create new editor tool (inherit from BrushUserToolState)
